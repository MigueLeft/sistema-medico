# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Offline desktop medical-records app ("Sistema Médico"): Tauri 2 (Rust + SQLite) backend with a React 19 + TypeScript frontend. The UI is built on **Material UI**: internal screens use MUI components themed to the «Clínica» design (`src/theme/clinica.ts`), wrapped by the app's own kit in `src/components/ui`; `/setup` and `/login` use the older theme in `src/theme/index.ts`. The codebase, identifiers, UI text and error messages are in **Spanish** — keep new code consistent with that (e.g. `crear_*`, `listar_*`, `useCrearPaciente`).

## Commands

Package manager is **pnpm**.

```bash
pnpm install
pnpm tauri dev        # full app (runs `pnpm dev` on :1420 + Rust backend)
pnpm tauri build      # production bundle (runs `pnpm build` first)
pnpm dev              # frontend only — invoke() calls will fail outside Tauri
pnpm build            # tsc -b && vite build (type-check + bundle)
pnpm lint             # eslint
cd src-tauri && cargo check   # fast Rust type-check
cd src-tauri && cargo test    # backend end-to-end tests (src/pruebas.rs)
cd src-tauri && cargo test flujo_completo   # a single test by name
```

Rust tests live in `src-tauri/src/pruebas.rs`: they build a temp SQLite DB, register state on `tauri::test::mock_app()` and call the command functions directly. There are no JS tests.

`src/routeTree.gen.ts` is generated by the TanStack Router Vite plugin from `src/routes/` and is gitignored; run `pnpm dev`/`pnpm build` to regenerate it if types complain.

## Architecture

### Frontend ↔ backend contract

- All data access goes through Tauri commands. The frontend never calls `@tauri-apps/api` `invoke` directly — use the wrapper in `src/lib/tauri.ts`, which converts Rust's `ErrorApp` (serialized as `{ message }`) into a JS `Error` so TanStack Query / toasts can read `error.message`.
- Rust structs use `#[serde(rename_all = "camelCase")]`; TS types in `src/features/*/types` mirror them in camelCase. Command arguments are passed as `{ id, payload }`, matching the Rust parameter names.
- Adding a command requires: the function in `src-tauri/src/commands/<area>.rs`, registering it in `generate_handler!` in `src-tauri/src/lib.rs`, models in `src-tauri/src/models/` (re-exported via `models/mod.rs`), then a service method + hook on the frontend.

### Frontend structure (`src/`)

- `features/<feature>/` — vertical slices, each with `services/` (thin `invoke` wrappers), `hooks/` (TanStack Query `useQuery`/`useMutation` with exported query keys; mutations invalidate keys and show `sonner` toasts on success/error), `components/`, `types/`, and an `index.ts` barrel. Import features through their barrel (`@/features/patients`).
- `routes/` — TanStack Router file-based routes. `__root.tsx` acts as the auth guard: if no users exist → `/setup`; no session → `/login`; otherwise renders `AppShell` (sidebar). Each internal route wraps its content in `<Page title>` from `components/AppShell.tsx`.
- `components/ui/` — the app's component kit: thin wrappers over **Material UI** (`Button`, `TextField`, `Select`, `Checkbox`, `Segmented`, `Modal`, `Card`/`Panel`, `MenuAcciones`, `DataTable`, `TerminologySearch` = MUI Autocomplete, `SectionNav`, `PendingList`, `AppointmentSlot`, …) that fix the design's conventions (label above the field, 34 px controls, tone-coloured chips). Screens import from `@/components/ui`; when a screen needs something the kit lacks, use the MUI component directly (never a raw `<button>`/`<input>`: MUI is used for its accessibility).
- Look and feel comes from three places: `theme/clinica.ts` (MUI theme + `TOKENS`, applied by `AppShell`'s `ThemeProvider`), `styles/clinica.css` (the design's CSS variables and the `cl-*` layout classes for composite rows such as `cl-entry`, `cl-slot`, `cl-pend`), and `styles/app.css` (`ap-*` page layout). MUI's `ButtonBase` resets border/background, so structures built on it re-declare them in `app.css` with a `.x.MuiButtonBase-root` selector. Dialogs/menus render in a portal outside `.cl-app`; `app.css` gives them the font.
- The consultation screen (`routes/consultas/$consultaId.tsx`) is a 6-step SOAP editor (the last step lists/creates entregables; each one is edited at `routes/entregables/$entregableId.tsx`); each step is a `Paso*` component in `features/consultas/components`. Consulta fields autosave on blur via `guardar_consulta`; sub-records (síntomas, diagnósticos, mediciones, tratamiento) save through their own commands.
- Form state initialised from loaded data follows one pattern (the lint rules forbid `setState` in effects): an outer component waits for the query, then mounts an inner form with a `key` and `useState` initialisers.
- `@/` alias maps to `src/`. Forms use react-hook-form + zod; `src/lib/forms.ts` has helpers for optional numeric fields.

### Backend structure (`src-tauri/src/`)

- `lib.rs` — builds the app, manages two pieces of state: `DbPool` (r2d2 SQLite pool) and `SessionState`.
- `session.rs` — the logged-in session lives **only in memory** in the Rust process (lost on app close). Commands obtain it with `session_state.get().ok_or(ErrorApp::SinSesion)?` and scope queries by `session.organizacion_id`.
- `error.rs` — `ErrorApp` / `Resultado<T>` is the return type of every command; `rusqlite` and `r2d2` errors convert via `?`.
- `db/` — DB file at `<app_data_dir>/sistema_medico.sqlite` (WAL, foreign keys on). `schema.sql` (v1) runs only on a new DB; then `run_migrations` applies each incremental script in order (`migracion_v2.sql`, which also seeds the catalogs; `migracion_v3.sql`) until `PRAGMA user_version` reaches `SCHEMA_VERSION` (currently 3). **Never edit `schema.sql` or an already-shipped migration** — add `migracion_vN.sql`, bump `SCHEMA_VERSION` and add its step to `run_migrations`.
- `models/mod.rs` — the `modelo!` macro declares a read model (camelCase-serialised struct + `from_row` reading each field from the column of the same name); every selected column must be aliased to the field name.
- `commands/catalogos.rs` — all reference catalogs (enfermedades, paraclínicos, procedimientos, motivos de ingreso, sistemas, medicamentos, términos…) share two generic commands, `listar_catalogo` / `guardar_catalogo`, driven by the `CATALOGOS` definition table. Adding a catalog = one entry there plus a `DefCatalogoPanel` in `features/catalogos/components/definiciones.tsx`.
- `commands/consultas.rs::exigir_borrador` — every command that writes into a consulta's sections calls it; a `cerrada` consulta is read-only.
- `audit.rs` — `audit::registrar(...)` writes to the append-only `auditoria` table; every command that inserts/updates/soft-deletes clinical data calls it inside the same transaction.
- `commands/entregables.rs` + `pdf.rs` — documents ("entregables") come from configurable templates (`plantilla_documento`: prefix + counter, paper size, an ordered JSON list of blocks, and whether emitting generates pendientes). `crear_entregable` makes a numbered **borrador** prefilled from the consulta; `guardar_entregable` edits it; `emitir_entregable` renders the PDF to `<app_data_dir>/entregables/<id>.pdf` (SHA-256 stored), makes it read-only and calls `generar_pendientes`. `pdf::generar_html_documento` walks the template's blocks in order — a new automatic block needs a match arm there, an entry in `bloque_automatico`, and its counterpart in `features/entregables/components/bloques.ts` + `VistaPreviaEntregable.tsx` (the on-screen preview mirrors the PDF). `plantilla_entregable` is only the shared letterhead.

### Data conventions (see header of `schema.sql`)

- Primary keys are TEXT UUID v4 generated in Rust.
- Clinical tables carry `organizacion_id`, `created_at/by`, `updated_at/by`, `deleted_at/by`; deletes are **soft-deletes**, so queries must filter `deleted_at IS NULL`.
- `nota_evolucion` and `auditoria` are append-only.
- Dates/times are ISO-8601 TEXT; booleans are INTEGER 0/1. `cita.fecha_hora` and `consulta.fecha` are **local** time without zone (`YYYY-MM-DDTHH:MM:SS`, see `util::ahora_local`); SQL filters by day with `substr(col, 1, 10)`.
- `antecedente` holds all six history groups (`tipo`: personal|familiar|quirurgico|hospitalizacion|alergia|habito); `intervencion_qx` is legacy and unused.
- `pendiente` = what the patient must bring next time. They are generated when an entregable is emitted (per its template: one per item or one per document) and can also be added by hand; `no_entregado` still counts as open. Any pendiente accepts an uploaded file (`adjuntar_archivo_pendiente`, stored under `<app_data_dir>/pendientes/`). A consulta cannot be closed while it has entregables in `borrador`.
- Each `paciente` has one `expediente` (code `HC-XXXXXXXX`) created in the same transaction.
- Passwords are hashed with argon2; initial setup (`crear_organizacion_inicial`) creates the organization, first user and `medico` role.
